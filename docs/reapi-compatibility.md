# REAPI compatibility investigation

## Status and scope

This is milestone 1 of [issue #22](https://github.com/OnixResearch/mantle/issues/22), reviewed on 2026-10-18. It is a compatibility design, **not an adapter, enabled configuration, real-service observation, or completion of issue #22**. Milestone 2 remains blocked by the service and producer prerequisites below. Native stdio/SSH/P2P contracts remain unchanged. [ADR 0118](../adr/0118-keep-reapi-transport-separate-from-mantle-output-authority.md) records the proposed future adapter boundary.

[Issue #15](https://github.com/OnixResearch/mantle/issues/15) must establish the final source/executable baseline before any implementation or parity evidence is attributed to it. The inspected native sources are a changing working tree, not a newly verified immutable release. No builds, tests, Nix evaluation, service probes, credential operations, or source uploads were performed for this investigation. Public primary-source retrieval was read-only. No REAPI runtime behavior is claimed.

## Exact primary-source baseline

All REAPI field references below mean the **v2.3.0** protocol at remote-apis commit **`e95641649b5b4d3c582c89daabfaabeb8189dd77`**, not the moving default branch:

- **[R]** [remote_execution.proto](https://github.com/bazelbuild/remote-apis/blob/e95641649b5b4d3c582c89daabfaabeb8189dd77/build/bazel/remote/execution/v2/remote_execution.proto): Execution, ActionCache, ContentAddressableStorage, **Capabilities**, action/command/tree/result/digest messages. Capabilities is in this file, not a separate capabilities proto. The [tag-ref response](https://api.github.com/repos/bazelbuild/remote-apis/git/ref/tags/v2.3.0) resolves the release tag to this commit.
- **[P]** [platform.md at the same commit](https://github.com/bazelbuild/remote-apis/blob/e95641649b5b4d3c582c89daabfaabeb8189dd77/build/bazel/remote/execution/v2/platform.md): optional standard platform lexicon, not proof that a server supports or enforces the properties.
- **[B]** [google/bytestream/bytestream.proto](https://github.com/googleapis/googleapis/blob/9415ba048aa587b1b2df2b96fc00aa009c831597/google/bytestream/bytestream.proto), googleapis commit **`9415ba048aa587b1b2df2b96fc00aa009c831597`**: Read, Write and QueryWriteStatus. This is a separate exact source pin, not a claim that remote-apis v2.3.0 pins that googleapis revision.
- **[O]** [google/longrunning/operations.proto at the same googleapis commit](https://github.com/googleapis/googleapis/blob/9415ba048aa587b1b2df2b96fc00aa009c831597/google/longrunning/operations.proto): Operation and best-effort CancelOperation. REAPI's stricter ExecuteResponse error convention takes precedence over generic Operation.error behavior.

A future generated client must lock its complete proto/import/compiler dependency closure separately. These source pins specify reviewed semantics, not a provisioned SDK or observed service version. Newer REAPI features are not silently part of this fragment.

### Identity translation and the selected minimal fragment

A general native derivation cannot be sent as `Command.arguments` unchanged and assumed compatible: logical absolute store paths, sandbox policy, input materialization, output finalization and signatures are not standardized by REAPI. Conversely, simply wrapping unverified ActionResult metadata in a native `RemoteBuildFinished` or signing it locally would create false execution evidence.

The proposed bounded fragment is therefore **a pinned Mantle-aware worker-side producer carried by REAPI**, not arbitrary Bazel action interoperability:

1. One already evaluated Linux x86-64 concrete action, one named input-addressed output with a known logical store path, network-none, immutable declared inputs and explicit resource/time/byte limits. No raw Nickel, dependency evaluation, source fetching, dynamic/CA output finalization, multi-output builds, accelerators or persistent workspace.
2. A reviewed bridge executable/runtime closure is either entirely in the approved input tree or fixed by an authorized service's immutable worker-image contract. The Action includes a regular-file semantic request and a canonical manifest of permitted input NARs. The semantic request contains native action identity, exact argv/env/system/prefix/expected output and enforced policy identities, **not** bearer material or job/attempt/fence/request timestamps. The bridge must recompute and validate these native facts and actually execute the declared action under the required policy; it is not a signing proxy for server-supplied metadata.
3. The bridge's fixed output paths are `result/output.nar`, `result/pathinfo.json`, `result/signed-action-result.json`, and `result/evidence.nar`. They are all regular files. The last contains the bounded complete native receipt/reference-scan/policy/signature object closure referenced by the signed record, with a fixed canonical manifest and no ambient paths. The bridge/output-envelope encoding and version must be finalized and source-bound during implementation; these path decisions do not claim that such a bridge or wire-envelope parser exists today.
4. The worker-side producer's signing capability must be separately authorized, scoped to the admitted producer policy and inaccessible to the untrusted build sandbox. It is injected by the service through an explicitly approved secret/capability boundary, **never uploaded in CAS**. A generic service without such a producer/evidence path is incompatible with signed native cold admission. Generating a client key or signing server output after download is not an alternative.
5. Canonical REAPI Command executes that exact bridge with only declared semantic-request/input paths, cwd at the input root, no PATH lookup or inherited semantic env, and exactly those sorted output paths. Freeze Command/Directory/Action bytes once. Put the translation version and pinned bridge/profile identity in the semantic input and a domain-separated Action.salt cache namespace; do not put transient attempts in the semantic action or salt. Including a different timeout changes the REAPI Action digest even when the native normalized key is unchanged.

The client retains a locally validated association between native action ref, normalized build key, semantic request/input-manifest digest, bridge/profile version, native per-dispatch plan and REAPI Action digest. It must not assume these different native identities are aliases. The signed native record binds the native action and outputs; exact action/receipt/input linkage must be checked against the frozen semantic request. REAPI metadata is not needed to grant that binding authority. A service may still schedule duplicate executions: this fragment requires a hermetic, repeatable action with no external effects, not exactly-once execution.

This intentionally small design does not remove milestone 2 scenarios or promise general Nix/Bazel parity. Broadening it requires a new reviewed semantic mapping and real acceptance, not accepting previously rejected fields.

## CAS and action-cache bytes versus signed admission

The same path applies to cold execution and a candidate found through GetActionResult:

1. Check the authorized origin/instance/profile and the active local attempt/fence before accepting any operation result. On a cache path, establish a current local admission attempt; do not replay a historical completion event.
2. Require a well-typed, complete response and successful execution status/exit code, or a cache candidate whose success is independently established by its native receipt. Normalize output **ordering only for comparison**, rejecting duplicate/conflicting paths. Fetch only the four allowed envelope files and their bounded authorized evidence closure. Treat raw stdout/stderr and worker metadata as diagnostics, never receipts.
3. Hash all downloaded/inline bytes against the advertised SHA-256 and exact sizes. Parse the NAR and independently compute native node identity, NAR SHA-256 and NAR size. Verify requested output name, store path/prefix, input-addressed identity and declared references; do not export unvalidated paths into the local store. Require complete referenced object content; a partial GetTree or available CAS root is not completeness.
4. Verify the native signed record and PathInfo signatures with full explicitly trusted public keys and current producer/revocation policy. Validate the native action ref, action receipt linkage, output object/PathInfo refs, reference-scan results, sandbox/network/producer/publication policy and artifact-attestation identity. A computed attestation digest or a signature's key **name** alone is not a verified signature. Require actual producer observations for every fact fed into `CandidateAdmissionFacts`; do not manufacture `true` observations from the record's own declarations.
5. Apply the existing native strong-reuse/conflict policy over immutable candidates. Only then translate verified facts into ordinary native admission/import, through the same byte/PathInfo/store boundaries. Recheck the current attempt fence before authoritative persistence/completion. Bytes left in physical CAS after failure do not become admitted PathInfo or a completed build.

Native immutable signed result records remain the authoritative discovery/admission records. A REAPI ActionResult is at most a locator for one of them. Generic REAPI `ExecutedActionMetadata.worker`, timestamps, `auxiliary_metadata`, server logs, Operation.name and `cached_result` are unsigned and cannot replace native provenance. Neither TLS authentication nor credentials give the server automatic output-signing trust. No additional signature authority or weakened claim strength is introduced.

## Authorization, uploads and credential boundary

A future opt-in service policy must be reviewed **before any capability RPC or upload**. The following is a configuration requirement inventory, not syntax supported by today's `remote-builders.ncl`:

| Required explicit operator fact | Rejection boundary |
| --- | --- |
| Named service owner and authorization to use that exact TLS gRPC origin, port, server identity/CA policy and exact instance name; separately authorized CAS/AC origins if different | No discovery, arbitrary public endpoints, plaintext fallback, redirects, inherited proxy routing or automatic origin/instance substitution. Operation/blob resource names cannot change origin or escape the selected instance. A cache URL, SSH endpoint or DNS record is not authorization. |
| Allowed operations: capabilities, CAS find/read/write, AC read, execution/wait and cancellation, plus data-retention/tenant-sharing restrictions | Explicit read-only cache use does not authorize execution or upload; service visibility and retention must be acceptable for the reviewed data classes. No client AC update/publication initially. |
| Approved exact upload manifest and closure identity; object/file/depth/total-byte/chunk/in-flight/time budgets; allowed store/source/proof classes | Default deny source/proof/secret-descriptor upload until specifically authorized. No repository, home directory, working tree, `.git`, ambient toolchain or credentials by broad recursive upload. Input NARs, bridge/runtime, request argv/env, filenames, policy metadata, digests and sizes all disclose information and belong in approval/accounting. |
| Opaque credential/provider handle, audience/scope/expiry policy, explicit TLS/mTLS/authorization mechanism | Resolve through the selected external provider at the adapter boundary; bounded access and fail on missing/expired/denied credentials. No provisioning, ambient ADC/env lookup, interactive login, shell helper or provider fallback by default. Do not reuse native bearer tickets as REAPI credentials. |
| Trusted producer identity, full verifying keys, signed evidence availability and current revocation/producer-policy source | Service access permission does not authorize signer trust. No generated keys or automatic trust-on-first-use; missing evidence is an admission blocker. |
| Immutable bridge/runtime identity and enforced system/prefix/sandbox/network/resource profile | Service-specific profile must be documented and observed in real acceptance. A capabilities advertisement or unrecognized Platform property is not enforcement. |

`FindMissingBlobs` requests may contain only digests in the already approved closure. Returned missing digests must be an exact subset; a missing-input `PreconditionFailure` can request retransmission only of that same closure, not arbitrary filesystem reads. Account metadata and all bytes, including retransmission, under explicit budgets. Canonical REAPI trees do not grant permission to follow symlinks out of the approved roots. Credential buffers/headers must stay out of CAS, semantic request files, derivation env, durable operation records, diagnostics and exception rendering. Persist only credential-free origin/instance/profile/digest/attempt/operation identifiers needed to resume.

Before execution, `GetCapabilities(instance_name = 1)` must return a non-deprecated version interval (`low_api_version = 4`, `high_api_version = 5`) containing 2.3.0, execution `exec_enabled = 2`, SHA256 execution/cache support and compatible limits. Capabilities absence is not permission to assume defaults. Cache `max_batch_total_size_bytes = 4` of zero means no advertised limit, **not** unlimited client allocation; intersect with local byte/message limits. Compression `IDENTITY` is always required by [R]; only uncompressed transfers are in this fragment. Cache-only endpoints cannot satisfy execution acceptance. Cancellation and enforced worker profile are additional service prerequisites not established by Capabilities.

## Transfer, operation identity and failure semantics

**ByteStream:** [R] defines uncompressed upload resource names as `{instance}/uploads/{uuid}/blobs/{hash}/{size}` (omit leading slash for empty instance), and reads as `{instance}/blobs/{hash}/{size}`. Use a generated UUIDv4 upload ID scoped locally to endpoint/instance/blob/attempt; no optional resource-name metadata. [B] `WriteRequest.resource_name = 1` must be set on each stream's first request and consistent thereafter, `write_offset = 2` must equal the committed cursor then advance exactly, `finish_write = 3` ends the stream, and `data = 10` carries bytes. QueryWriteStatus returns `committed_size = 1`, `complete = 2`; on disconnect it may report fewer bytes than the client sent. Validate bounded nonnegative cursor/complete combinations, resume the **same** upload only under its current authorization, and fail on impossible/regressed observed status. NOT_FOUND requires an explicitly bounded restart, not trusting saved progress. A concurrent completed uncompressed upload can terminate successfully with full committed size even if this client sent fewer bytes; record that honestly. Server acknowledgement establishes transport progress only, not native content or output authority. Reads must finish with the exact bounded hash/size; empty responses do not reset idle-progress deadlines. Compressed offset semantics and delta transfer are excluded, not approximated by native transfer cursors.

**Operations:** persist a credential-free local association of `(authorized origin, instance, REAPI action digest, Operation.name)` with `(native job, attempt, fence, normalized key, profile)`. Operation.name is service-local opaque state, not a global identity, URL or worker credential. Check ExecuteOperationMetadata.action_digest against the frozen action when present; mismatches reject. Bind any updates to the connection/request and stored operation, and reject changing names, wrong response Any type, malformed completion or `Operation.error` (forbidden by [R] Execute). Unknown local operations/attempts are not adopted from a server message. RequestMetadata.action_id/tool_invocation_id are diagnostic correlation only.

After receiving a valid operation name, reconnect via `WaitExecution(name = 1)` rather than blindly issuing Execute again. Keep the action and operation association across reconnects. If disconnect occurs before any operation name, execution outcome is unknown: REAPI has no Execute idempotency token. Do not claim no execution occurred; any explicit bounded re-execution keeps the semantic action digest, invalidates the old local attempt and fences its results. Even one Execute may execute multiple times. Server ExecutionStage may move EXECUTING back to QUEUED; stage telemetry does not mutate native assignment authority.

| Observed failure | Required handling |
| --- | --- |
| Invalid/denied credentials, TLS/origin/instance mismatch, PERMISSION_DENIED / UNAUTHENTICATED | Authentication/authorization failure; terminal until explicit operator correction. Do not switch provider/endpoint or grant trust. |
| INVALID_ARGUMENT, unsupported capabilities/profile/policy, malformed digest/tree/response | Request/compatibility rejection; no automatic retry or fallback that drops the guarantee. |
| FAILED_PRECONDITION with missing command/input blobs | Input-sync failure; inspect bounded MISSING details and allow only already authorized closure retransmission. No new-source acquisition. Other preconditions are not all missing-input retries. |
| RESOURCE_EXHAUSTED, UNAVAILABLE, INTERNAL, transport disconnect | Infrastructure/transport/queue failure, not nonzero program exit or successful build. Respect bounded RetryInfo/backoff within explicit native retry policy; reconcile a known operation before re-execution. RetryInfo is not authorization or an unbounded wait. |
| ExecuteResponse.status non-OK, including DEADLINE_EXCEEDED or CANCELLED | Execution/infrastructure outcome; no output admission even if partial result/stdout is present. [R] requires errors here and prohibits caching non-OK results. Native queue/total deadline remains separate from Action.timeout. |
| status OK with ActionResult.exit_code nonzero | Failed user action, not a successful build/cache reuse. Keep bounded diagnostics; do not auto-rerun as infrastructure or import partial outputs. |
| Missing/tampered/wrong-prefix/unsigned/mismatched evidence or stale fence | Output-import/admission failure; terminal for that candidate/attempt. Never local-fallback to bypass evidence or turn transferred bytes into success. |

Cancellation first invalidates local acceptance authority, then requests `CancelOperation` for the stored operation if explicitly supported. [O] makes cancellation best effort and allows UNIMPLEMENTED; [R] does not require general Operations support and requires execution errors in ExecuteResponse.status, unlike generic Operation.error. A transport close, acknowledged CancelOperation or local timeout is **not proof that all remote executions stopped**. Keep an unknown/continuing remote-effect report where needed and reject late results at the local fence. A service lacking observed cancellation cannot meet a promise of enforced remote termination; document that incompatibility rather than inventing a guarantee.

## Available service evidence and the exact milestone-2 blocker

Read-only searches covered `config/`, `lib/`, `examples/`, documentation/README and Cairn context for REAPI, ByteStream, remote-executor/cache, Buildbarn/BuildGrid/BuildBuddy/EngFlow and grpc/grpcs endpoint configuration, plus available `local://` handoffs for REAPI/service context. The effective native configuration contracts were inspected directly. No explicitly authorized compatible REAPI service/instance, REAPI credential handle, approved upload closure, or trusted REAPI-connected native producer was supplied by these sources.

Concrete existing configuration is **not** such authorization:

- `src/remote_farm_config.rs::RemoteTransportMode` and `lib/remote-builders.ncl` enumerate only native stdio/ssh-stdio/p2p.
- `secretspec.toml` declares native `TICKET_VERIFIER_KEY` and `RESULT_SIGNING_KEY`; it neither names a REAPI origin/instance nor authorizes repurposing these credentials.
- [examples/projects/remote-build-loopback/README.md](../examples/projects/remote-build-loopback/README.md) explicitly exercises a local production framed-stdio child with native one-use tickets. Its `gallery-builder` name is not a gRPC service.
- The archived production-farm design mentions REAPI as a possible future adapter, not a deployment or upload grant. Existing docs explicitly exclude REAPI from native transfer compatibility claims.

This is evidence of **missing supplied authorization**, not a claim that no suitable service exists anywhere. No DNS inference, public endpoint selection, local fake service, credential lookup/provisioning, or capability/execute probe was attempted.

Milestone 2 needs an operator-provided, reviewable authorization bundle containing all of:

1. Exact permitted TLS gRPC origin(s), server identity policy, instance, service owner, use/quota/retention/tenant restrictions and permission for capabilities/CAS/AC-read/execute/wait/cancel.
2. An externally provisioned credential handle with the correct audience/scope and explicit provider policy, or explicit authorization for a genuinely anonymous service. No credential values belong in this document.
3. Exact allowed representative fixture/tool/runtime/source closure and byte/time/resource limits, with explicit source-upload permission where needed. The requested work has **not** authorized uploading this repository.
4. A compatible immutable worker/bridge profile enforcing the requested Linux/store-prefix/sandbox/network/resource semantics, and a real producer that emits the complete signed native output/evidence closure after actual execution, with explicitly trusted full public keys and current producer/revocation policy. A stock REAPI server plus CAS alone does not satisfy this requirement.
5. The #15 immutable baseline executable/source receipt and a bounded adapter implementation source/executable identity. Neither documentation nor an older binary supplies this prerequisite.
