## Independent musl 1.2.5 compatibility check

An actual executable linked with Nix musl 1.2.5 (loader `/nix/store/22jf61rk865il2svdy1zd5s0zz6wvmpq-musl-1.2.5/lib/ld-musl-x86_64.so.1`) initially executed successfully with absolute hash-bearing `DT_NEEDED`. The same binary after the isolated pure planner wrote `$ORIGIN/../../0123456789abcdfghijklmnpqrsvwxyz-musl/lib/libanswer.so` into `DT_NEEDED` and matching `$ORIGIN` RUNPATH failed at runtime (exit 127):

```text
Error loading shared library $ORIGIN/../../0123456789abcdfghijklmnpqrsvwxyz-musl/lib/libanswer.so: No such file or directory
```

The upstream musl 1.2.5 source at `ldso/dynlink.c::load_library` opens slash-bearing `name` literally, while its `fixup_rpath` expands `$ORIGIN` only for RUNPATH. This is a direct behavioral blocker for the currently specified origin-relative NEEDED on the actual GCC 10 musl loader, not merely a missing cache entry.

A throwaway comparative probe rewrote the same musl binary's NEEDED to basename `libanswer.so` while preserving the hash literal in a sole `$ORIGIN/../../0123456789abcdfghijklmnpqrsvwxyz-musl/lib` RUNPATH. With an empty runtime environment, the executable passed from the first prefix and an independently copied second prefix (both exit 0); a copy with a wrong hash in RUNPATH exited 127 with `Error loading shared library libanswer.so`. This supports an alternative link/lookup strategy but **does not satisfy the current normative hash-bearing origin-relative NEEDED requirement**. Such an alternative requires an explicit Cairn spec/ADR decision and production GCC runtime build. A source-authored musl loader patch is the other possible strategy; no patch or patch behavior was produced by this check.

With an adversarial `LD_LIBRARY_PATH` containing an unrelated `libanswer.so` returning a different answer, the basename-NEEDED alternative exited 1 in the original prefix, and a wrong-hash RUNPATH copy also exited 1 instead of failing to load. The ambient path bypasses the selected hash. The basename alternative is **not** an accepted Cairn implementation.

In an isolated scratch-only source-built musl 1.2.5 experiment, a guarded `$ORIGIN/` handler for slash-bearing, hash-bearing `DT_NEEDED` made the first executable and a copied second-prefix executable both exit 0 with empty environment and adversarial `LD_LIBRARY_PATH`. A wrong hash exited 127 even under adversarial `LD_LIBRARY_PATH`; an existing non-hash `../../outside` target exited 127 with `Invalid argument`. A user namespace provided a real file-capability `AT_SECURE=1` witness (the same static auxv probe reported 0 before `setcap` and 1 afterward); the capability-marked relocated executable exited 127 with `Invalid argument`. No global basename lookup semantics were changed. This is an experimental source modification under scratch, **not** a production patch, source-pin validation, StageX GCC proof, or Cairn completion.

## Scratch loader security review (not adopted)

The exact upstream musl tarball downloaded from `https://musl.libc.org/releases/musl-1.2.5.tar.gz` matched the cached archive byte-for-byte (raw SHA256 `a9a118bbe84d8764da0ea0d28b3ab3fae8477fc7e4085d90102b8596fc7c75e4`). Nix `nix-prefetch-url --unpack` stripped the archive wrapper and hashed its inner tree as `sha256-xNKVsRfEK7TkSiYrxPho9ap8MWGix7nVHLecGW0D7kE=`. An isolated program calling the **actual Mantle** `crunch_build::fetcher::unpack_archive_file` on those same upstream bytes retained the wrapper and produced `sha256-WLIl4Mb82rsOQm/nQ9TmBD067Nxqm6yNwGGDZ1jS+Y8=`, exactly the pinned `bootstrap/musl-full.ncl` source NAR. The apparent source mismatch was a different unpacking convention, **not** authority to replace the pin.

Independent read-only review caught three initially exploitable scratch-loader cases: an additional `../` preceding the valid hash, a symlinked hash member, and a symlinked library each loaded an attacker library (program exit 1 rather than required refusal 127). It also identified expansion applied to `dlopen`, a newline parser typo, and an accidental global basename alias. The subsequently rebuilt scratch-only musl loader has no worktree RUNPATH, scopes expansion to `DT_NEEDED`, walks selected paths and referring ancestors with no-follow file descriptors, derives the exact parent-hop count from the referring output's single hash-looking member, and rejects ambiguous multiple hash-looking ancestors. The revised test executable's ELF PT_INTERP names that scratch-built loader. Flat and nested transitive DSO chains, including a copied second prefix, exited 0; wrong-depth nested valid-hash targets, extra parent hops, hash-member and library symlinks, wrong hashes, newline-bearing names, and a false-hash ancestor exited 127. An actual `AT_SECURE=1` file-capability test exited 127, while `dlopen`'s literal `$ORIGIN` name remained unresolved exactly as on upstream musl. A second DSO's bare `libanswer.so` resolved its independent library despite the first hash-pinned DSO using the same basename. These are **scratch experiments only**; ordinary upstream raw slash handling and arbitrary `LD_PRELOAD` symbol behavior are not changed or claimed.

Independent review still **blocks production**: a single attacker-controlled hash-looking origin under an arbitrary copied prefix is not authenticated by lexical spelling. No production patch or `bootstrap/musl-full.ncl` edit exists. Security requires an externally trusted immutable flat-store-root/closure authority, including restrictions on writable replacement races, before a loader patch can claim root binding. No actual StageX GCC10 loader was built by this experiment.
