## Decisions

### 1. Nixpkgs support is a producer adapter, not native Mantle evaluation

**Choice:** Add nixpkgs support by producing `foreign-derivation-graph-v1`, `foreign-package-index-v1`, and import receipts from concrete Nix derivation facts. The producer may run host Nix or another Nix-compatible evaluator before artifact creation, but Mantle consumption must read only the lowered artifacts.

**Rationale:** Mantle's stable boundary is build-shaped. Importing nixpkgs as source language would bring in flakes, overlays, `callPackage`, stdenv conventions, and package-set replacement semantics. A producer adapter lets users benefit from nixpkgs while preserving Mantle's frontend-neutral import core.

### 2. Build the first slice around concrete derivation closures

**Choice:** The first implementation should accept `.drv` files or `nix derivation show --recursive`-style JSON and produce graph/package-index artifacts. Package-name lookup may be generated by a producer shell, but the package index must contain only lowered names, systems, root derivation identities, aliases, provenance refs, and unsupported metadata classes.

**Rationale:** Concrete derivations are the seam where Nix frontend semantics have already been resolved. Starting there avoids solving full nixpkgs evaluation and makes offline fixtures possible.

### 3. Make substitution-first useful before rebuild compatibility

**Choice:** Treat cache/substitution hints, especially `cache.nixos.org`, as explicit trust-scoped policy data. The initial operator value is importing a concrete nixpkgs closure, planning it in Mantle, and accepting substitutes through Mantle's existing PathInfo/NAR/signature policy. Rebuilding imported nixpkgs derivations is a later compatibility level.

**Rationale:** Large nixpkgs closures are expensive and often depend on sandbox assumptions Mantle may not yet emulate. Substitution-first gives an honest integration path without overclaiming build compatibility.

### 4. Keep Nix hash identity separate from Mantle receipt identity

**Choice:** The adapter must preserve upstream Nix derivation identity with Nix-compatible hash semantics while using BLAKE3 for Mantle import receipts, policy digests, and translated artifact identities. Any use of the vendored `nix-compat` crate must be audited for Mantle's local BLAKE3 modifications before it is used for Nix-compatible `.drv` identity.

**Rationale:** Mantle intentionally uses BLAKE3 for its own derivation layer, while Nix `.drv` identity and cache protocols rely on Nix-compatible hashing. Mixing those domains would silently make cache lookup, receipt comparison, and trust claims wrong.

### 5. Use Snix crates by layer

**Choice:** Use `nix-compat` for `.drv`/ATerm, store path, Nix hash, NAR, and NARInfo parsing only after hash-domain audit. Use `snix-store` and `snix-castore` for PathInfo/content-store/cache surfaces when they preserve Mantle's existing store admission policy. `snix-build` is not a primary solution for nixpkgs support because Mantle owns scheduling/orchestration. `snix-eval` may become a producer backend later, but it must stay outside the import core and normal consumption path.

**Rationale:** The crates are useful primitives, not a package-set integration strategy. The adapter should reuse proven format and transport code while keeping semantic ownership explicit.

### 6. Receipt language stays conservative

**Choice:** Nixpkgs import receipts must say exactly what was admitted: graph provenance, derivation closure identity, package-index roots, hash-domain policy, cache/substitution policy, sandbox compatibility metadata, and non-claims. Build success, output trust, package correctness, bootstrap parity, and reproducibility require later evidence.

**Rationale:** Nixpkgs integration is attractive enough that users may overread import admission as "Mantle supports nixpkgs". The receipt and docs must prevent that overclaim.

## Risks / Trade-offs

- Host-Nix producer mode is practical but not Nix-free; the receipt must record producer provenance and non-claims.
- A `.drv` parser path may need upstream-compatible `nix-compat` behavior or a hash-mode split because Mantle's vendored copy has BLAKE3 derivation hashing changes.
- Many nixpkgs derivations may require sandbox capabilities, fixed-output fetch behavior, or reference-scanning behavior that Mantle does not yet support; these should become deterministic blockers.
- Package indexes can become huge; the first slice should keep checked fixtures small and bounded.
- Optional `snix-eval` integration is tempting, but adding it too early risks turning the adapter into a second Nix frontend inside Mantle.
