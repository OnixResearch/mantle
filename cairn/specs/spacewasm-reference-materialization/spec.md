# Spacewasm Reference Materialization Specification

## Purpose

Defines the `spacewasm-reference-materialization` capability.

## Requirements

### Requirement: SpaceWasm reference materialization uses one typed profile

r[mantle.spacewasm_materialization.profile] Mantle MUST define a typed Nickel profile that binds the exact SpaceWasm source, dependency lock, Rust toolchain, targets, build features, support matrix, runner configuration, fixture classes, retention, and non-claims, and runtime code MUST consume a deterministic checked export.

#### Scenario: Complete profile is admitted
- GIVEN every required profile field is present and its generated export is fresh
- WHEN reference materialization planning runs
- THEN Mantle MAY plan the declared cohort under one deterministic profile identity.

#### Scenario: Profile or export drifts
- GIVEN the Nickel source and generated runtime export differ or a required field is absent
- WHEN planning runs
- THEN Mantle MUST fail closed before source acquisition or build execution.

### Requirement: Upstream source and dependencies are exact

r[mantle.spacewasm_materialization.source] Mantle MUST bind an exact upstream commit, source archive BLAKE3, Cargo lockfile, dependency closure, Rust toolchain, license, notice, and imported-corpus provenance and MUST NOT resolve a floating branch or network dependency during the build.

#### Scenario: Exact source closure is available
- GIVEN source, lockfile, dependencies, toolchain, license, notices, and corpus provenance match the profile
- WHEN source admission runs
- THEN Mantle MAY expose immutable inputs to the sandbox.

#### Scenario: A mutable or stale input is supplied
- GIVEN a branch ref, archive, dependency, lockfile, toolchain, or provenance fact does not match the profile
- WHEN source admission runs
- THEN Mantle MUST deny the cohort without fetching a fallback.

### Requirement: Build outputs retain role-specific identities

r[mantle.spacewasm_materialization.build] Mantle MUST build the declared no-std library and host diagnostic artifacts offline and MUST retain separate identities for source, library, runner, target, feature configuration, and build closure.

#### Scenario: Declared targets build
- GIVEN the exact admitted source and closure
- WHEN sandboxed compilation runs for the declared targets
- THEN each output MUST bind its target, features, toolchain, source, and closure identities.

#### Scenario: One target or feature fails
- GIVEN a declared build cannot complete
- WHEN build evidence is assembled
- THEN the failure MUST remain target/feature-specific and the bundle MUST NOT report the cohort as completely built.

### Requirement: Fixture and corpus inputs are reproducible

r[mantle.spacewasm_materialization.fixtures] Mantle MUST materialize positive and negative MVP, streaming, allocation, feature, trap, and fuel fixture classes plus imported spectest/fuzz corpus descriptors with exact bytes, generation inputs, expected class, provenance, and BLAKE3 identities.

#### Scenario: Fixture pack is regenerated
- GIVEN identical admitted fixture inputs and generators
- WHEN materialization repeats
- THEN every promoted fixture byte identity and expected class MUST match.

#### Scenario: Fixture bytes or expectations drift
- GIVEN regenerated bytes, class, provenance, or generator identity differs
- WHEN fixture verification runs
- THEN Mantle MUST reject stable-corpus promotion and report the drift.

### Requirement: Recorded checks remain bounded evidence

r[mantle.spacewasm_materialization.evidence] Mantle MUST record each declared build, test, and fixture outcome as passed, failed, skipped, unavailable, or unsupported and MUST bind the exact command/configuration/input/output identities without treating upstream CI configuration as local execution evidence.

#### Scenario: A declared check passes locally
- GIVEN the admitted cohort and bounded check complete successfully
- WHEN evidence is emitted
- THEN the result MUST bind the local closure, inputs, outputs, and check identity.

#### Scenario: A tool or check is absent
- GIVEN `spacewasm-check`, continuous fuzzing, a target runner, or another declared check is unavailable
- WHEN evidence is emitted
- THEN the result MUST say unavailable or skipped and MUST NOT synthesize a passing outcome.

### Requirement: The reference bundle is rehashable and complete

r[mantle.spacewasm_materialization.bundle] Mantle MUST emit a versioned bundle whose manifest binds every required source, closure, toolchain, binary, profile, fixture, report, license, notice, parent edge, and non-claim member by BLAKE3 and MUST provide deterministic verification independent of store paths.

#### Scenario: Consumer remeasures a complete bundle
- GIVEN every required portable member is present and unchanged
- WHEN bundle verification runs outside the producing store path
- THEN all member and parent identities MUST verify.

#### Scenario: A member is missing or tampered
- GIVEN any required member, digest, role, or parent edge is absent or mismatched
- WHEN verification runs
- THEN the bundle MUST be rejected as incomplete or tampered.

### Requirement: Materialization decisions have a functional core

r[mantle.spacewasm_materialization.functional_core] Profile validation, support-matrix comparison, identity material construction, bundle planning, expected-result evaluation, and diagnostic ordering MUST be pure deterministic logic over explicit in-memory inputs.

#### Scenario: Identical facts are evaluated twice
- GIVEN identical normalized profile, source, build, fixture, and result facts
- WHEN the core evaluates them
- THEN it MUST produce identical plans, identities, decisions, and diagnostics without filesystem, network, process, clock, environment, or output effects.

### Requirement: SpaceWasm reference evidence preserves non-claims

r[mantle.spacewasm_materialization.nonclaims] Mantle MUST reject any promotion of reference materialization evidence into SpaceWasm correctness, memory safety, WebAssembly conformance, flight qualification, sandbox effectiveness, consumer runtime admission, or release eligibility.

#### Scenario: Bundle is used as a downstream input
- GIVEN a verified reference bundle
- WHEN a consumer imports it
- THEN the bundle MAY prove exact materialization facts but MUST require a separate consumer-owned admission decision.

#### Scenario: Report requests a stronger role
- GIVEN a report labels the bundle as certified, flight-qualified, correct, safe, sandboxed, production-ready, or release-eligible
- WHEN report validation runs
- THEN Mantle MUST reject the unsupported claim.

### Requirement: Reference materialization has positive and negative validation

r[mantle.spacewasm_materialization.validation] The change MUST include positive exact-source, offline-build, deterministic-fixture, complete-bundle, and independent-remeasurement cases plus negative floating-source, stale-lock, wrong-toolchain, unsupported-feature, omitted-license, corpus-drift, unavailable-check, report-tamper, incomplete-bundle, and overclaim cases.

#### Scenario: Reference materialization changes
- GIVEN profile, acquisition, build, fixture, evidence, or bundle behavior changes
- WHEN closeout evidence is assembled
- THEN focused tests, positive and negative fixtures, machine-contract freshness, bundle verification, Cairn validation, and lifecycle gates MUST run or record an exact blocker and next-best check.
