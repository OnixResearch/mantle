# ADR 0088: Keep live build-state subscriptions in a bounded Mantle daemon

## Status

Accepted (2026-10-06). This decides the provider boundary, not proof of end-to-end behavior or compatibility with a future Molten adapter.

## Context

A batch build's aggregate JSON report and evaluation NDJSON stream are not a subscription to the *current* fact set. Live goal, worker, reservation, terminal-outcome, and service-readiness facts must be observable without giving the observer store, evidence, scheduling, or admission authority. The change proposal calls this an extension of ADR 0080, but `adr/0080-separate-coordination-from-batch-building.md` was **absent from the isolated baseline** at review time (although `adr/README.md` lists it). We separately read the original Accepted ADR at `/home/brittonr/git/OnixResearch/mantle/adr/0080-separate-coordination-from-batch-building.md`: its Decision (lines 37-66) defines three planes, daemon independence, and a Molten provider mandate; its Consequences (lines 105-117) require bounded, redacted facts and restart retraction. This ADR extends those plane/lifetime constraints while explicitly narrowing the provider mandate **for this one live-state subscription surface**: use the daemon-owned fallback until Molten's required integration is demonstrated. It neither edits ADR 0080 nor invents text for its initially missing isolated copy.

The local Aspen Molten source reviewed here is `/home/brittonr/git/OnixResearch/aspen` at revision `81baf80cb667a22277be22c140d34829e5c7da7f` (its `Cargo.toml` identifies package `molten` version `0.1.0`, Preserves `5.0.0-rc.7`, and Syndicate `0.44.0-rc.3`; it declares AGPL-3.0-or-later). The local path identifies the inspected checkout, **not** a durable runtime dependency or provider configuration. This is source inspection, not a Mantle dependency or executable compatibility test:

## Decision drivers

- Admit only versioned facts with bounded fact size, count, filter size, subscribers, pending events, and frame size.
- Provide an initial filtered set followed by change events, with unambiguous owner-loss cleanup and restart invalidation.
- Keep local Unix-socket availability optional: a stalled or missing daemon cannot delay or change a build.
- Do not import unproven socket, filter, backlog, restart, or ownership guarantees from Molten merely because its explicit observe/retract fixtures pass.

## Decision

Use the narrow Mantle-owned coordination daemon and `crunch-live-state-core` as the current live-state provider, superseding ADR 0080 Decision lines 64-66 **only as to using Molten for live-state subscriptions**. The building, coordination, and evidence plane separation and all other provider decisions in ADR 0080 remain unchanged. A pure `#![no_std]` + alloc core defines `Fact { version, id, owner, kind, subject, state }` and `Filter { owner?, kind?, subject_prefix? }`; the five kinds are `goal`, `worker`, `reservation`, `outcome`, and `service_readiness`. The building plane owns deterministic identity `fact_id(owner, kind, subject)` with BLAKE3 domain separation; the daemon validates identity and maintains an in-memory `LiveSet` indexed by that ID. A publisher's **connection** owns its published facts, regardless of the fact's descriptive owner string. A changed fact is republished at its stable ID; a state that ceases to hold is retracted. Disconnect retracts all facts published on that connection. A worker loss observed by a still-connected producer requires the producer to retract the affected worker and in-flight goal facts; the daemon cannot infer that loss from the owner string or a timer.

Hard caps: 2,048 serialized bytes per fact, 4,096 simultaneous facts, 256 serialized bytes per filter, 128 subscribers, 64 pending delta events per subscriber, and 4,096 bytes per NDJSON frame. Atomic snapshot captures share an aggregate 64 MiB byte budget; a subscription beyond that budget is rejected. Snapshot facts stream individually before `snapshot_end`; a full delta queue or a frame write stalled for more than five seconds drops the subscriber rather than blocking publication. Reject invalid or oversized input. Matching snapshots have deterministic ordering and then a snapshot terminator before subsequent matching changes. The socket is local-only. The daemon may serve and remove facts but has no store handle, evidence-authoring role, receipt authority, or admission/scheduling/output-publication veto.

The build only attempts nonblocking, bounded, best-effort publication when `MANTLE_COORDINATION_SOCKET` is set; with no socket or daemon, build correctness and result publication stay independent. Publication is change-driven, not a heartbeat. On daemon restart all facts disappear with its process memory; prior socket connections are gone and **cannot receive retraction messages from the dead process**. A new raw connection receives `reset` with a fresh generation, requiring consumers to discard every old fact and resubscribe. The stateful `crunch_coordination::SubscriptionClient` makes this invalidation explicit to its consumer: `disconnected()` on EOF and `receive()` on a new `reset` emit sorted per-ID `SubscriptionEvent::Retract` for every retained fact, **before** exposing the new generation's `Reset` and snapshot. The client, not the dead daemon, synthesizes restart retractions. Within one generation the daemon sends per-ID retractions on publisher disconnect or explicit state changes. Prior publishers must reconnect and republish; there is no durable replay.

The provider seam is the daemon's bounded publish/retract/subscribe behavior and the wire contract, not a second interchangeable coordination model or a dormant Molten adapter. Reconsider Molten only with an executable integration proving exact bounded filters, socket lifecycle, initial/current matching set, subsequent retracts including owner disconnect, restart reset, caps/backpressure, and a defensible dependency/license pin; until then do not claim compatibility or pull it into Mantle.

## Rejected alternatives

- Repurpose one-shot NDJSON or poll the final JSON report: neither supplies current-set ownership and retraction semantics.
- Make each build process serve subscribers: couples observers to a running batch process.
- Direct Molten adoption today: exact/whole-value wildcard patterns and explicit assertion transitions are useful primitives, but the reviewed local API and fixtures do not provide Mantle's required conjunctive bounded filter, Unix endpoint, publisher-connection ownership, reset protocol, or subscriber backpressure without additional integration.
- A durable fact store, timer-based stale-fact inference, or store/evidence authority in the daemon: all turn an ephemeral observation service into an incorrect authority.

## Consequences and non-claims

This decision introduces a small daemon-owned socket protocol and pure state core instead of adopting Molten's runtime/dependency tree. An unreachable service degrades observation, never the build. Live facts are volatile statements about a daemon generation, **not** evidence, receipts, a release input, or proof of successful output. The reviewed Aspen tests prove their own scoped assertions and retract behavior only; no Molten/Mantle runtime interoperability, build identity equivalence, worker-loss detection, or production safety is established by this source review. Operator and wire examples are in `docs/live-build-state.md`.

Reserve `BlockingPublisherSession` for explicit doctor/diagnostic calls: its synchronous socket/ACK waits do not belong on a scheduler, remote-service, or cache critical path. `BestEffortPublisher` moves that session to one background thread behind a 64-command `try_publish`/`try_retract` queue; a full or failed queue degrades observation, and `finish(deadline)` waits at most 100 ms. The build's own asynchronous publisher likewise bounds final flushing to 100 ms outside goal scheduling. These bounded waits define a policy, **not** a demonstrated end-to-end equality of build outputs and receipts; that comparison needs an actual CLI build run.
